## The governing rule

> **Pull on a schedule into `raw`. Never let a consumer query the source system live.**

Every integration failure mode gets easier when there's a landing zone between you and the source:

- The source going down doesn't take your reports with it
- You're not putting query load on someone else's production system
- You can replay, reprocess, and backfill from data you control
- Schema changes at the source break one loading job, not every downstream query
- You have a record of what the source said at the time, which matters when numbers are disputed

The cost is latency. That's almost always the right trade.

## SSIS patterns

### Truncate and reload — the default

The simplest thing that works, and naturally idempotent.

```
Execute SQL Task:  TRUNCATE TABLE raw.SalesExtract
       ↓
Data Flow Task:    Source → (minimal transform) → OLE DB Destination (Fast Load)
       ↓
Execute SQL Task:  EXEC mart.RefreshMasterSales @Year = ?
```

Rules:
- **Load into a table you defined**, never "create table if not exists" auto-generated by the destination → [why](07-project-layout.md#should-the-tool-create-your-tables)
- **No business logic in the data flow.** Type conversion at most. Everything else happens in SQL, where it's version-controlled, testable, and readable.
- **Use OLE DB Destination with Fast Load** and a sensible batch/commit size (10,000–50,000 rows). The default row-by-row insert is orders of magnitude slower.
- Add `LoadedUtc` and `LoadBatchId` columns with defaults.

### Append with a batch ID

When you need history of what each extract contained:

```sql
DECLARE @BatchId bigint = NEXT VALUE FOR dbo.LoadBatchSeq;
-- SSIS passes @BatchId as a parameter into the data flow
```

Then reprocessing a batch means deleting that `LoadBatchId` and re-running — still idempotent, with history retained.

### Staging then swap, for large loads

Load into `stg.SalesExtract_New`, validate it, then swap:

```sql
BEGIN TRAN;
    TRUNCATE TABLE raw.SalesExtract;
    INSERT raw.SalesExtract SELECT * FROM stg.SalesExtract_New;
COMMIT;
```

Keeps the target queryable during the slow part of the load, and gives you a validation gate before publishing.

### Error handling

- **Set `MaximumErrorCount` to 0** so failures actually fail. A package that reports success while having loaded nothing is the worst outcome.
- **Redirect error rows** to a rejects table rather than failing the whole package on one bad row. → [poison record](00-glossary.md#reliability-patterns)
- **Configure logging** to a SQL table, and have the Agent job alert on failure *and* on not-having-succeeded-recently.
- **Use package configurations / environment variables** for connection strings — never hardcode, and never check in credentials.

### Idempotence in SSIS

Ask of every package: **if this runs twice, is the result the same?**

- Truncate-and-reload: ✅ yes
- Append without a key: ❌ duplicates
- Append with a batch ID and a delete-then-insert: ✅ yes
- File import that moves the file after processing: ✅ effectively yes

## Idempotent file loading

For file-based feeds, track what you've already loaded:

```sql
CREATE TABLE dbo.FileLoadLog
(
    FileName      nvarchar(400) NOT NULL PRIMARY KEY,
    FileHash      binary(32)        NULL,
    RowsLoaded    int               NULL,
    LoadedUtc     datetime2(0)  NOT NULL DEFAULT SYSUTCDATETIME(),
    Status        varchar(20)   NOT NULL
);
```

Before loading, check whether the filename has already been processed. If a filename can be reused with different content, hash the file and compare that instead.

**Also: move processed files to an archive folder.** A file that's still in the inbox is unambiguously unprocessed, which makes recovery after a failure obvious rather than a guessing game.

## Linked servers

A configured connection to another server, queryable via four-part names.

```sql
SELECT * FROM RemoteSrv.RemoteDb.dbo.SomeTable;
```

Convenient and frequently a performance disaster.

### The core problem

**Predicates often don't get pushed to the remote side.** SQL Server may pull the entire remote table across the network and filter locally — the plan shows a "Remote Query" operator with a huge row count and no useful detail about what happened over there.

Statistics on remote objects are unreliable, cardinality estimates are guesses, and joins between local and remote tables are frequently catastrophic.

### Guidance

**Do:**
- Use `OPENQUERY` to force the filtering to happen remotely:

```sql
SELECT * FROM OPENQUERY(RemoteSrv,
    'SELECT Id, Name FROM dbo.BigTable WHERE LoadDate >= ''2025-01-01''');
```

The string is executed *on the remote server*, so only matching rows cross the wire. Note the doubled quotes — string escaping inside `OPENQUERY` is genuinely annoying, and it's a common source of dynamic-SQL bugs.

- Pull into a local `#temp` or `raw` table first, then join locally
- Give the linked server login minimal permissions
- Consider whether SSIS on a schedule is a better fit than a live link

**Don't:**
- Join local and remote tables in one query over large volumes
- Let a website or report query through a linked server
- Use a linked server for anything transactional (that's DTC territory)

## Historians and time-series sources

Process historians (AspenTech IP.21, OSIsoft PI, Honeywell PHD, Wonderware) come up constantly in industrial settings and behave nothing like relational databases.

### The conceptual difference

A historian is **not relational**. It's tag-based time-series storage: repeat areas, records, definitions, all optimized for "give me this tag's values over this time range." Trying to think about it relationally will fight you at every step.

Aspen's **SQLplus** looks like SQL and mostly isn't — it has its own extensions for time-weighted aggregation and interpolation that have no ANSI equivalent, and the semantics of a `SELECT` against a repeat area are not what you'd guess.

### Access routes

- **Aspen SQLplus ODBC driver** — the usual path, consumable from SSIS or as a linked server
- **Aspen Process Data REST / OLEDB**
- Vendor-specific .NET APIs

### Two hard-won cautions

**1. Don't let a website query a historian live, through a linked server or otherwise.**

Historian queries over wide time ranges are slow, and they put real load on a box that operators depend on for live process monitoring. A badly-formed report query can degrade something people are watching to run a plant. Pull on a schedule into `raw.*`, and let everything downstream hit SQL Server.

**2. Pull aggregated data, not raw compressed points.**

Historians store compressed values with deadbands — a tag might have millions of points per day. Use the historian's own aggregation (`AGGREGATES` with a period in SQLplus) to downsample on their side. Pulling raw and aggregating in SQL Server moves enormous volumes across the wire for no reason.

**Always bound the time range.** An unbounded historian query is how you find out what a timeout looks like.

### Landing shape

```sql
CREATE TABLE raw.HistorianTagData
(
    TagName    varchar(100)  NOT NULL,
    SampleUtc  datetime2(0)  NOT NULL,
    Value      float             NULL,   -- float is correct here: sensor readings
    Quality    varchar(20)       NULL,   -- historians report quality; keep it
    LoadedUtc  datetime2(0)  NOT NULL DEFAULT SYSUTCDATETIME(),
    CONSTRAINT PK_HistorianTagData PRIMARY KEY CLUSTERED (TagName, SampleUtc)
);
```

Clustered on `(TagName, SampleUtc)` because every query is "this tag, this time range." That index choice is the whole performance story for time-series data.

**Keep the quality flag.** Historians distinguish good values from bad, uncertain, or interpolated ones, and averaging across bad-quality samples silently corrupts your numbers. Filter on it in the transform, not on the way in.

**Watch time zones.** Historians frequently store local plant time. Record what you received, convert explicitly, and document which it is.

### Documentation

There are **no good third-party books on IP.21** — it's a niche vendor product in a small market. What exists:

- **AspenTech Support site** (support.aspentech.com) — the real documentation plus a knowledge base of solution articles. Requires a customer login, which your site almost certainly has.
- **AspenTech University** training courses on IP.21 administration and SQLplus
- **The SQLplus help file** shipped with the install — better than people expect
- **Whoever at your plant has run it for fifteen years.** Not a joke. Institutional knowledge is the real documentation for historians.

## IIS and web application access

### App pool identity

When an IIS application pool runs as a domain account, `w3wp.exe` runs as that account, and any outbound SMB or SQL connection authenticates as it. If the account can reach a network share or a database, so can the site.

**Default `ApplicationPoolIdentity`** presents on the network as the *computer account* (`DOMAIN\SERVERNAME$`), not a user — which only reaches resources where the machine account itself was granted access. That's usually why people switch to a domain account.

### The double-hop problem

If you enable Windows Authentication **with impersonation** (`<identity impersonate="true" />`), the thread runs as the *visitor's* account. Browser → IIS is hop one; IIS → SQL Server is hop two. **NTLM will not forward credentials across that second hop**, so you get access denied even though the user has permissions.

Fixing it requires Kerberos with constrained delegation and correct SPNs. If you're not impersonating, none of this applies — which is the usual reason not to impersonate.

### Recommended setup

- App pool runs as a **gMSA** or a dedicated domain service account
- That account is a SQL Server login mapped to a database user
- The user is in a role with `SELECT` on `mart.vw_*` and `EXECUTE` on specific procedures — **not** `db_datareader` on everything, and certainly not `db_owner`
- The application uses parameterized queries exclusively
- Connection pooling is on (default), so keep connection strings identical across the app — a differing string creates a separate pool

```sql
CREATE ROLE AppReader;
GRANT SELECT ON SCHEMA::mart TO AppReader;
GRANT EXECUTE ON SCHEMA::mart TO AppReader;
ALTER ROLE AppReader ADD MEMBER [DOMAIN\svc_WebApp];
```

Granting on the *schema* rather than object-by-object means new views and procedures are covered automatically — one of the practical payoffs of the schema layout.

## Service accounts

**Avoid using a personal domain account** for services, app pools, or SQL Agent jobs, even though it works.

Three reasons:
1. **The service dies when you do** — role change, departure, or a disabled account takes the application with it
2. **Password rotation silently breaks things** — the pool fails to start, or share access breaks, with a confusing error
3. **Audit logs show your name** on everything the application writes, forever

**Use a gMSA (group Managed Service Account).** Active Directory rotates the password automatically, you never type it anywhere, and it's supported as a SQL Server service account, an IIS app pool identity (IIS 8+), and a SQL Agent proxy.

Failing that, a dedicated service account with a documented owner, a password that doesn't expire (and is stored in a password manager), and a note in your runbook about what breaks if it's disabled.

## Handling schema drift

The source changed shape and nobody told you.

### Detection

```sql
-- snapshot the shape of a raw table and compare over time
SELECT c.name, t.name AS TypeName, c.max_length, c.is_nullable
FROM   sys.columns AS c
JOIN   sys.types   AS t ON t.user_type_id = c.user_type_id
WHERE  c.object_id = OBJECT_ID('raw.SalesExtract')
ORDER  BY c.column_id;
```

Store this and diff it after each load. A new column appearing is usually harmless; a *type* change or a removed column is not.

### Mitigation

- **Land data in a tolerant shape.** Wider `varchar` in raw than you strictly need buys you room, since you're validating in the transform anyway.
- **Fail loudly on unexpected columns** rather than silently ignoring them — an ignored new column is data you're not capturing.
- **Validate row counts and key metrics after every load.** → [reconciliation](03-refresh-patterns.md#reconciliation)
- **Alert on new unmapped values** in `ref` lookups — that's often your first signal the source added a category.

SSIS is particularly brittle here because it binds column metadata at design time. A column added at the source causes a validation failure; a column *removed* causes a package failure. Neither is subtle, which is a mild virtue.
